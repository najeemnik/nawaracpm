# Nawara Studio — چشم‌انداز محصول، استراتژی PWA و ایده‌های ویژه

**تاریخ:** ۸ اکتوبر ۲۰۲۶
**نام رسمی محصول:** **Nawara Studio — CPM (Client Project Management)**

---

## بخش ۱ — نام رسمی

| نقش | نام |
|---|---|
| محصول اصلی | **Nawara Studio — CPM (Client Project Management)** |
| اپلیکیشن تسک‌ها | **Nawara Tasks** (پیشنهاد) |
| پورتال مشتری (بعداً) | **Nawara Client** (پیشنهاد) |

هر زیربرنامه نام خود را دارد، اما همه یک برند و یک «مغز» هستند: **یک دیتابیس، یک API.**

---

## بخش ۲ — پاسخ به سؤال PWA شما

### سؤال: آیا می‌توان فقط بخش تسک‌ها را PWA جدا گرفت؟

**بله — و این یکی از بهترین تصمیم‌هایی است که می‌توانید بگیرید.**

نکتهٔ کلیدی: این کار خیلی ارزان‌تر از چیزی است که به نظر می‌رسد، چون **۹۵٪ سیستم مشترک است**. چیزی که جدا می‌شود فقط این است:

```
یک دیتابیس  →  یک API امن  →  دو Shell جداگانه
                                 ├── Nawara Studio — CPM   (دسکتاپ/دفتر)
                                 └── Nawara Tasks          (موبایل/سایت)
```

هر Shell فقط شامل: یک `manifest.json`، یک Service Worker، آیکون خودش و یک مسیر ورود. منطق، permissionها، دیتابیس و API دقیقاً یکی هستند.

### دو راه فنی

**راه الف — دو زیردامنه (توصیهٔ قطعی من)**

```
app.nawara.af    → Nawara Studio — CPM
tasks.nawara.af  → Nawara Tasks
```

- هر کدام manifest و Service Worker مستقل، آیکون مستقل، cache مستقل
- نصب کاملاً جدا؛ نوتیفیکیشن و badge هر کدام به خودش نسبت داده می‌شود
- **ورود یک‌باره برای هر دو:** کوکی session روی `.nawara.af` با `Secure` + `HttpOnly` + `SameSite=Lax`
- این روش همان چیزی است که مرجع رسمی PWA گوگل توصیه می‌کند

**راه ب — یک دامنه، مسیر جدا (اگر کنترل زیردامنه ندارید)**

```
nawara.af/        → CPM      (scope: /)
nawara.af/tasks/  → Tasks    (scope: /tasks/)
```

- در Chrome و Edge کار می‌کند و هر دو جداگانه نصب می‌شوند
- اما مرجع رسمی این حالت را «به‌شدت توصیه نمی‌کند»: مرورگر آن‌ها را واقعاً دو اپ جدا حساب نمی‌کند؛ اگر فقط اپ بیرونی نصب باشد، نوتیفیکیشن و badge اپ درونی به اپ بیرونی نسبت داده می‌شود. حافظه هم مشترک است.

**توصیه: راه الف.** اگر بعداً دامنه گرفتید، راه ب هم قابل ارتقا به الف است.

### اصل اصلاح‌شده: هر دو اپ، روی هر دستگاه

> **تصحیح مهم (۸ اکتوبر ۲۰۲۶):** نسخهٔ قبلی این جدول CPM را به دسکتاپ محدود کرده بود. این اشتباه بود.

**هر دو اپلیکیشن روی موبایل و دسکتاپ، هر دو قابل نصب هستند.** چیزی که محدود می‌شود دستگاه نیست — **سطح دسترسیِ کاربر است**، و آن هم فقط با لاگین مشخص می‌شود:

| کاربر | می‌تواند نصب کند | بعد از لاگین کجا می‌رود |
|---|---|---|
| Head Engineer / Admin | **CPM و Tasks، هر دو، روی هر دستگاه** | CPM (با سوئیچرِ رفتن به Tasks) |
| Project Admin | **CPM و Tasks، هر دو، روی هر دستگاه** | CPM |
| کارمند / انجنیر | **فقط Tasks، روی هر دستگاه** | Tasks (صفحهٔ «کار من») |
| صاحب پروژه | بعداً: فقط Nawara Client | پورتال مشتری |

جزئیات کامل طراحی نصب و مسیر‌یابیِ نقش در [`docs/11_INSTALL_AND_ROLE_ROUTING_FA.md`](./11_INSTALL_AND_ROLE_ROUTING_FA.md).

کارمند شما تنظیمات، بخش‌ها، وزن‌ها و یوزرها را نمی‌بیند — اصلاً در اپش نیست.

### محدودیت‌های واقعی که باید از اول بدانید

| موضوع | واقعیت ۲۰۲۶ |
|---|---|
| نصب روی Android | خودکار (پیشنهاد نصب می‌آید) |
| نصب روی iPhone | دستی: Safari → Share → Add to Home Screen |
| Push روی Android | کامل، از داخل مرورگر هم کار می‌کند |
| Push روی iPhone | فقط iOS 16.4+ **و فقط اگر اپ نصب شده باشد**؛ از تب مرورگر کار نمی‌کند |
| HTTPS | اجباری برای Service Worker و نصب |
| حافظهٔ iPhone | بعد از حدود ۷ روز عدم استفاده، cache و IndexedDB پاک می‌شود — باید `persistent storage` درخواست کنیم و طراحی آفلاین را با این فرض بسازیم |

برای Push به VAPID key و برای reminder واقعی به یک cron سمت سرور نیاز داریم؛ خود PWA وقتی بسته است نمی‌تواند یادآوری کند.

## بخش ۳ — یافته‌های تحقیق

### Notion در ۲۰۲۶ چه شده است؟

| تحول | توضیح |
|---|---|
| Notion 3.0 (سپتامبر ۲۰۲۵) | AI از «پیشنهاددهنده» به **عامل اجراکننده** تبدیل شد؛ تا ۲۰ دقیقه کار مستقل |
| Custom Agents (فوریه ۲۰۲۶) | عامل‌هایی که روی زمان‌بندی یا trigger خودکار اجرا می‌شوند |
| Enterprise Search | جستجو در Slack، Drive و ابزارهای متصل |
| هزینه | فقط در پلن Business: حدود ۲۰ دلار برای هر کاربر در ماه |

**مهم‌ترین درس برای ما** — یک پیش‌بینی که در تحلیل‌های ۲۰۲۶ تکرار شده:

> بهترین پیاده‌سازی‌ها عامل‌های کمتری دارند، اما هر عامل به یک «Worker قطعی» (deterministic) وصل است برای بخش‌هایی که نباید به reasoning مدل زبانی سپرده شوند.

ترجمه برای Nawara: **AI پیشنهاد می‌دهد، کد قطعی تصمیم می‌گیرد.**

یعنی:
- AI می‌تواند لیست تسک‌های پیشنهادی برای یک پروژه را بنویسد
- اما **ساخت واقعی آن‌ها را موتور template انجام می‌دهد**، نه AI
- AI هرگز approve نمی‌کند، هرگز فیصدی را تغییر نمی‌دهد، هرگز permission نمی‌دهد
- AI می‌تواند خلاصهٔ پروژه بنویسد، اما اعداد از محاسبهٔ قطعی می‌آیند

این باعث می‌شود AI مفید باشد بدون اینکه دادهٔ شما را خراب کند.

همچنین: Notion با ۱۰ کارمند برای شما حدود ۲۰۰ دلار در ماه می‌شود — و باز هم ساختمانی نیست (نه وزن سکشن، نه تأیید head engineer، نه پورتال مشتری ساختمانی).

### استانداردهای مدیریت پروژهٔ ساختمانی که پیدا کردم

**۱. Last Planner System و شاخص PPC** — استاندارد طلایی lean construction

```
PPC = (تسک‌های انجام‌شده ÷ تسک‌های قول‌داده‌شده) × ۱۰۰
```

- فقط یک عدد نیست؛ ارزش اصلی در **کد دلیل** است: طراحی، مصالح، پیش‌نیاز، هوا، نیرو، سایر
- تیم‌های بالغ: **۷۵ تا ۸۵٪**
- زیر ۶۰٪ یعنی فرایند آماده‌سازی خراب است
- بالای ۹۰٪ معمولاً یعنی تیم کمتر از توانش قول می‌دهد تا عدد خوب نشان دهد

**۲. Earned Value Management (EVM)** — استاندارد اندازه‌گیری پیشرفت

```
EV  = فیصدی واقعی × بودجهٔ کل
PV  = فیصدی برنامه‌ریزی‌شده × بودجهٔ کل
SPI = EV ÷ PV        →  زیر ۱٫۰ یعنی عقب
CPI = EV ÷ هزینهٔ واقعی
EAC = بودجه ÷ CPI    →  پیش‌بینی هزینهٔ نهایی
```

نکتهٔ مهم: برای پروژه‌های ساختمانی، **وزن‌های سکشن شما دقیقاً همان «بودجهٔ وزن‌دار» است که EVM لازم دارد.**

**۳. Make-Ready / شش‌هفته lookahead** — قبل از اینکه کاری قول داده شود، موانعش (نقشه، مجوز، مصالح، نیرو، تجهیزات، ایمنی) بررسی می‌شود. کاری که آماده نیست اصلاً نباید قول داده شود.

**۴. آفلاین واقعی در سایت** — ابزارهای حرفه‌ای ساختمانی (مانند Procore) روی این تأکید دارند: در سایت اینترنت قطع است. ثبت پیشرفت، عکس و زمان باید بدون اینترنت کار کند و بعداً همگام شود. این‌جا PWA از هر وب‌سایتی جلو می‌زند.

## بخش ۴ — ایده‌های ویژه: «استفاده آسان، کار پیچیده»

ده ایده دارم. پنج تای اول را جدی توصیه می‌کنم.

### 🌟 ایده ۱ — موتور تعهد (Nawara Commitments)
**استفاده:** کارمند آخر هفته یک صفحه می‌بیند: تسک‌هایی که قول داده بود. جلوی هر کدام **Done** یا **Not Done + انتخاب یک دلیل از ۶ گزینه**. دو لمس.

**کاری که می‌کند:** PPC برای هر کارمند، هر هفته، هر پروژه؛ نمودار Pareto دلایل تأخیر؛ تشخیص خودکار «قول‌های غیرواقعی» در مقابل «موانع واقعی». با استاندارد LPS هم‌خوان است و مقایسه با نُرم صنعت (۷۵–۸۵٪) را ممکن می‌کند.

### 🌟 ایده ۲ — پیش‌بینی هوشمند (Earned Value بدون ورودی اضافه)
**استفاده:** شما فقط «ارزش قرارداد» پروژه را یک‌بار وارد می‌کنید. همین. فیصدی‌ها را همان‌طور که الان می‌زنید می‌زنید.

**کاری که می‌کند:** سیستم وزن‌های شما را به پول تبدیل می‌کند و می‌گوید: «شما ۶۲٪ کار انجام داده‌اید اما باید ۷۱٪ می‌بودید — ۱۴ روز عقب هستید» و «با این روند، تاریخ تحویل ۲۳ مارچ می‌شود، نه ۹ مارچ». برای صاحب پروژه: یک عدد قابل فهم.

> احتیاط فنی: شاخص SPI در ۳۰٪ پایانی پروژه به ۱٫۰ میل می‌کند و بی‌معنا می‌شود؛ در آن مرحله باید «اختلاف زمانی به روز» و مسیر بحرانی را نشان داد. این را درست پیاده می‌کنیم.

### 🌟 ایده ۳ — آفلاین واقعی برای سایت
**استفاده:** کارمند در سایت اینترنت ندارد. اپ را باز می‌کند، تسک را تمام‌شده می‌زند، عکس می‌گیرد، می‌بندد.

**کاری که می‌کند:** همه‌چیز در IndexedDB دستگاه می‌ماند؛ وقتی اینترنت برگشت خودکار همگام می‌شود؛ اگر دو نفر تغییر متفاوت داده باشند، سیستم تضاد را نشان می‌دهد نه اینکه یکی را قورت بدهد. عکس‌ها در صف آپلود می‌مانند.

این همان چیزی است که اپ‌های حرفه‌ای ساختمانی را از وب‌سایت جدا می‌کند.

### ⭐ ایده ۴ — گواهی تصویری (Photo Proof)
برای تسک‌های حساس (بتن‌ریزی، برق‌کاری، IFC)، submit بدون عکس قبول نمی‌شود. عکس با **زمان و مختصات** مهر می‌خورد (حتی آفلاین، چون GPS از ماهواره می‌آید نه اینترنت). شما قبل/بعد را کنار هم می‌بینید. برای اختلاف با مشتری، سند دارید.

### ⭐ ایده ۵ — آماده‌سازی (Make-Ready)
قبل از اینکه تسکی به حالت «قول‌داده‌شده» برود، ۶ چک‌باکس موانع ظاهر می‌شود. تسکی که نقشه ندارد اصلاً قول داده نمی‌شود — در نتیجه بعداً Blocked نمی‌شود. مشکل را قبل از وقوع حل می‌کند، نه بعد از تأخیر.

### 💡 ایده ۶ — نمودار S و عکسِ فوریِ پیشرفت
هر هفته یک snapshot از فیصدی‌ها. نمودار S: برنامه در مقابل واقعیت. تشخیص پروژه‌ای که هفته‌ها فیصدی‌اش تکان نخورده ولی «فعال» است.

### 💡 ایده ۷ — شاخص اعتماد (First-Pass Yield)
چون تأیید شما در سیستم است، رایگان به دست می‌آید: چند درصد تسک‌های هر کارمند بار اول تأیید شده؟ چند بار تجدیدنظر خورده؟ متوسط زمان انتظار برای تأیید شما چند ساعت است؟ این نشان می‌دهد مشکل از کارمند است، از وضوح تسک، یا از کندی تأیید.

### 💡 ایده ۸ — Command Palette (Ctrl+K)
یک جستجوی سراسری Notion-style: بنویسید «برق پروژه فلانی» و مستقیم بروید. ارزان، اما حس «پیشرفته بودن» را بیشتر از هر چیز دیگری منتقل می‌کند.

### 💡 ایده ۹ — پین کردن تسک روی پلان
تسک را روی نقشهٔ طبقه پین کنید. روی موبایل: «این تسک، این نقطه». برای پروژه‌های آپارتمانی بسیار کاربردی است بعداً.

### 💡 ایده ۱۰ — راپور خودکار هفته‌وار
هر جمعه، یک راپور PDF/HTML به زبان دلخواه (دری/پشتو/انگلیسی) ساخته می‌شود: پیشرفت، تسک‌های تمام‌شده، عقب‌مانده‌ها، عکس‌ها. شما تأیید می‌کنید، برای مشتری می‌رود.

### پیشنهاد نهایی من
اگر فقط سه تا انتخاب کنید: **ایده ۱ + ۲ + ۳**. با هم چیزی می‌سازند که هیچ ابزار عمومی برای شما ندارد: یک عدد در روز از کارمند، یک مقدار قرارداد از شما — و خروجی‌اش قابلیت اعتماد تیم، پیش‌بینی تحویل و دلایل واقعی تأخیر است.

## بخش ۵ — برنامهٔ مرحله‌ای به‌روز‌شده

| مرحله | محتوا | تغییر نسبت به قبل |
|---|---|---|
| ۱ | ایمن‌سازی داده، مهاجرت، `.gitignore` | **حالا بسیار کم‌خطرتر است** چون پروژه‌ها تستی‌اند |
| ۲ | Task API و انتقال وضعیت | بدون تغییر |
| ۳ | اتصال تسک به پیشرفت **+ موتور Earned Value** | افزوده شد |
| ۴ | Template تسک و تولید خودکار هنگام ساخت پروژه | بدون تغییر |
| ۵ | Task Workspace + **PWA جداگانهٔ Nawara Tasks** + آفلاین | PWA از مرحلهٔ ۷ به این‌جا آمد |
| ۶ | نوتیفیکیشن، صدا، reminder، موتور تعهد (PPC) | افزوده شد |
| ۷ | سه‌زبانگی + PWA اصلی CPM | سبک‌تر شد |
| ۸ | پورتال مشتری (بعداً PWA سوم) | بدون تغییر |
| ۹ | AI Assistant (اختیاری) | بدون تغییر |
| ۱۰ | QA، performance، rollout | بدون تغییر |

**تغییر مهم:** با این ترتیب، کارمندان شما در **مرحلهٔ ۵–۶** اپ نصبیِ خود را می‌گیرند — نه در مرحلهٔ ۸. یعنی ارزش واقعی خیلی زودتر به دست‌تان می‌رسد.
