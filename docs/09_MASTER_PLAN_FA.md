## بخش ۲ — یک ریسک که باید همین امروز بسته شود

پکیج هاستینگ شما **MySQL** را ذکر کرده اما چیزی دربارهٔ **SQLite** ننوشته است — در حالی که دیتابیس فعلی پروژه SQLite است.

این را الآن باید معلوم کنیم، چون:
- اگر `pdo_sqlite` فعال باشد → ادامه می‌دهیم، هیچ تغییری لازم نیست
- اگر فعال نباشد → باید **همین حالا** به MySQL برویم. امروز این تصمیم یک تغییر کوچک در لایهٔ دیتابیس است؛ شش مرحلهٔ بعد تبدیلِ کل schema و triggerها می‌شود

**کاری که از شما می‌خواهم:** فایل `tools/hosting-check.php` را با FTP در `public_html` هاست آپلود کنید، در مرورگر باز کنید و خروجی‌اش را برای من بفرستید. هیچ رمزی نشان نمی‌دهد و چیزی تغییر نمی‌دهد — فقط گزارش محیط است. بعد از آن پاکش کنید.

سه مورد دیگر که در همان صفحه باید در cPanel چک کنید:

| مورد | کجا | چرا |
|---|---|---|
| **Subdomains** | cPanel ← Domains ← Subdomains | ساخت `app.` و `tasks.` |
| **SSL برای زیردامنه** | cPanel ← SSL/TLS Status ← Run AutoSSL | بدون SSL روی زیردامنه، PWA نصب نمی‌شود |
| **Cron Jobs** | cPanel ← Advanced ← Cron Jobs | بدون آن، یادآوری و هشدار تأخیر کار نمی‌کند |

> **یادداشت ترافیک:** ماهانه ۳۰ گیگ دارید. عکس‌های سایت اگر خام آپلود شوند این را زود تمام می‌کنند. برای همین تصویر **در مرورگر فشرده می‌شود** (حدود ۲۰۰–۳۰۰ کیلوبایت به‌جای ۳–۵ مگابایت) و بعد آپلود می‌گردد. این در طراحی لحاظ شده است.

### موج ۱ — پایه

#### مرحله ۱ — آماده‌سازی هاست، امنیت و بازسازی دیتابیس
- تأیید محیط هاست (اسکریپت بالا) و تصمیم نهایی SQLite / MySQL
- انتقال دیتابیس به **خارج از Web Root** + `.htaccess`
- افزودن `.gitignore` و خروج `data/` و `uploads/` از Git
- **بازسازی تمیز دیتابیس** (کاربران فعلی تستی‌اند): schema جدید، بدون دادهٔ زاید
- اجرای migration ۰۰۱ تا ۰۰۹
- امن‌سازی session: کوکی روی دامنهٔ اصلی، `Secure`، `HttpOnly`، بازسازی شناسه پس از لاگین
- خاموش کردن نمایش خطا در production
- دادهٔ seed: statusها، sectionها/وزن‌ها، ۳ پروژهٔ نمونه برای تست

**خروجی:** پایهٔ امن و تمیز روی هاست واقعی.
**تست:** لاگین کار می‌کند؛ هیچ فایل دیتابیس از مرورگر قابل دسترسی نیست؛ تغییرات در Git ثبت نمی‌شوند.

#### مرحله ۲ — سیستم سه‌نقشه و صفحهٔ مدیریت
- سه نقش: **ادمین**، **کارمند**، **صاحب پروژه** — همه از یک صفحه تعریف می‌شوند
- permissionهای سراسری + دسترسی و permissionِ **per-project**
- صفحهٔ مدیریت: ساخت یوزر، تعیین نقش، تعیین permission، تعیین دسترسی پروژه
- **مسیر‌یابی بر اساس نقش:** کارمند → فقط Tasks؛ ادمین → هر دو؛ مشتری → پورتال خودش
- اجرای واقعی permissionها در **سرور**، نه فقط در UI
- تغییر password/permission یا غیرفعال‌سازی → sessionهای قبلی قطع شوند

**خروجی:** کنترل کامل دسترسی از صفحهٔ ادمین.
**تست:** ماتریس permission برای هر سه نقش؛ کارمند با درخواست مستقیم به API ادمین باید **۴۰۳** بگیرد.

### موج ۲ — تسک و پیشرفت

#### مرحله ۳ — هستهٔ تسک و جریان کار
- Task API: ساخت، ویرایش، assign، شروع، Blocked، Submit for Review، Approve، Request Revision
- انتقالِ هر وضعیت در **یک تراکنش** با بررسی actor، عضویت و policy
- assignment تک‌نفره و چندنفره با دو حالت: نتیجهٔ مشترک / هر کارمند سهم خود را submit کند
- گزینهٔ **Review Required** برای هر تسک (روشن/خاموش با دست ادمین)
- comment، checklist، attachment، activity log
- انتقال داده‌های Priorities فعلی به Tasks (بدون حذف)
- **فشرده‌سازی تصویر در مرورگر** پیش از آپلود

**خروجی:** موتور تسک با همان workflow که تأیید کردید.
**تست:** کارمند فقط submit می‌کند، نمی‌تواند خودش نهایی کند؛ مسیر approve/revision درست است.

#### مرحله ۴ — اتصال تسک به پیشرفت + موتور پیش‌بینی
- اتصال تسک به Section و Item
- با تأیید ادمین، وضعیت item در همان جدول فعلی به‌روزرسانی می‌شود → **فیصدی موجود شما خودکار بالا می‌رود**
- `progress_mode` برای هر پروژه: `manual` (پروژه‌های قدیمی) / `task_driven` (پروژه‌های جدید)
- **Earned Value:** ارزش قرارداد (ورودی دستی، بعداً) → EV، PV، SPI، CPI، پیش‌بینی تاریخ تحویل و هزینهٔ نهایی
- نمودار S: برنامه در مقابل واقعیت با snapshot هفتگی

**خروجی:** تأیید تسک → پیشرفت پروژه خودکار؛ و یک عددِ قابل فهم برای مشتری.
**تست:** پروژهٔ manual تغییر نمی‌کند؛ پروژهٔ task_driven دقیقاً به اندازهٔ وزنِ item بالا می‌رود؛ SPI درست حساب شود.

> نکتهٔ فنی: شاخص SPI در ۳۰٪ پایانی پروژه به ۱٫۰ میل می‌کند و بی‌معنا می‌شود. در آن مرحله «اختلاف زمانی به روز» و مسیر بحرانی نشان داده می‌شود، نه SPI.

#### مرحله ۵ — قالب تسک و تولید خودکار
- قالب تسک برای هر Section Item (مثل «نقشهٔ برق» → سه تسک استاندارد)
- هنگام ساخت پروژهٔ جدید، تسک‌ها از قالب ساخته می‌شوند
- مهلت هر تسک نسبت به تاریخ شروع پروژه
- در همان فرم **Add New Project**، بخش **اختیاری** برای assign کردن هر تسک به کارمند
- **حفظ کامل نمایش و گزینه‌های فعلی** Projects (Add / Update / New Project)

**خروجی:** ساخت پروژه = تسک‌های استاندارد آماده + امکان assign در همان لحظه.
**تست:** تعداد و مهلت تسک‌های تولیدشده؛ assign اختیاری؛ ظاهر Projects تغییر نکرده باشد.

### موج ۳ — اپلیکیشن‌ها

#### مرحله ۶ — Nawara Tasks (PWA نصبی + آفلاین)
- زیردامنهٔ `tasks.`، manifest، service worker، آیکون
- **دکمهٔ نصب در نوار بالا** (Chrome/Edge: نصب مستقیم؛ iPhone: راهنمای Add to Home Screen)
- نماها: **کار من**، فهرست، برد/کانبان، تقویم
- **آفلاین واقعی:** ثبت پیشرفت بدون اینترنت، ذخیره در دستگاه، همگام‌سازی خودکار بعداً
- گواهی تصویری: عکس با مهر زمان و مکان (حتی آفلاین)

**خروجی:** اپی که کارمند روی موبایل نصب می‌کند و در سایتِ بدون آنتن هم کار می‌کند.
**تست:** نصب روی اندروید و آیفون؛ قطع اینترنت و ثبت تسک؛ همگام‌سازی بعد از وصل شدن.

#### مرحله ۷ — نوتیفیکیشن، صدا و موتور تعهد
- نوتیفیکیشن درون‌برنامه با زنگ، شمارنده و **صدا** + تنظیمات شخصی و ساعات سکوت
- **Push** برای هر دو اپ، با حذف اعلان تکراری بین آن‌ها
- یادآوری و هشدار تأخیر با **cron سمت سرور** و ارجاع به Head Engineer
- **موتور تعهد (PPC):** کارمند آخر هفته دو لمس می‌زند — انجام شد / نشد + یک دلیل
- داشبورد: PPC هر کارمند و پروژه + نمودار Pareto دلایل تأخیر

**خروجی:** هیچ تسکی بی‌خبر عقب نمی‌ماند؛ و قابلیت اعتماد تیم قابل اندازه‌گیری می‌شود.
**تست:** ارسال درست بر اساس ماتریس اعلان‌ها؛ رعایت ساعات سکوت؛ محاسبهٔ درست PPC.

#### مرحله ۸ — Nawara Studio CPM (PWA) + سه زبان
- زیردامنهٔ `app.`، manifest، service worker، دکمهٔ نصب در نوار بالا
- ترجمهٔ کامل رابط: **انگلیسی (پیش‌فرض)**، **دری**، **پشتو** + RTL خودکار
- انتخاب زبان در تنظیمات هر کاربر
- Command Palette (Ctrl+K) برای جستجوی سراسری
- سوئیچر اپ در هدر برای رفتن بین CPM و Tasks

**خروجی:** هر دو اپ نصبی، سه‌زبانه، آمادهٔ استفادهٔ روزانه.
**تست:** نصب هر دو اپ روی یک دستگاه؛ تعویض زبان؛ درستی RTL؛ لینک بین دو اپ.

### موج ۴ — تکمیل

#### مرحله ۹ — پورتال صاحب پروژه
- زیردامنهٔ سوم و اپ سوم: **Nawara Client**
- مشتری فقط موارد منتشرشده را می‌بیند: پیشرفت کلی، پیشرفت هر بخش، گزارش‌های تأییدشده، فایل‌های منتشرشده، مراحل اصلی
- برای **هر مورد جداگانه** تعیین می‌شود: قابل‌مشاهده؟ نیاز به تأیید؟ اجازهٔ کامنت؟ اجازهٔ دانلود؟
- اعلان بر اساس مرحله (milestone)، نه هر تسک داخلی
- درخواست تغییر همیشه نیازمند دلیل

**تست:** مشتری هیچ تسک داخلی، کامنت داخلی یا بارکاری کارمند را نمی‌بیند.

#### مرحله ۱۰ — دستیار هوشمند (اختیاری)
طبق درس Notion ۲۰۲۶: **AI پیشنهاد می‌دهد، کد تصمیم می‌گیرد.**
- پیشنهاد لیست تسک از توضیح پروژه → اما ساخت واقعی توسط قالب، نه AI
- پیش‌نویس گزارش هفته‌وار → اعداد از محاسبهٔ قطعی می‌آیند
- خلاصهٔ وضعیت پروژه به زبان دلخواه
- **AI هرگز approve نمی‌کند، فیصدی را تغییر نمی‌دهد، دسترسی نمی‌دهد**
- کلید AI فقط در سرور، هرگز در مرورگر یا Git

**تست:** خروجی AI هیچ تغییر مستقیمی در دیتابیس ایجاد نمی‌کند بدون تأیید شما.

#### مرحله ۱۱ — کیفیت، سرعت و استقرار
- تست‌های خودکار برای: لاگین، ماتریس permission، جریان تسک، محاسبهٔ پیشرفت، آفلاین
- pagination و رفع کندیِ queryها
- تمرین backup و بازگردانی
- مستندات استقرار و راهنمای استفاده
- بررسی نهایی امنیت
