# راهنمای امن نصب و انتقال NawAra CPM

این مرحله، دیتابیس NawAra را همچنان منبع اصلی اطلاعات نگه می‌دارد؛ اما برای نصب عملی باید **فایل دیتابیس و فایل‌های پروژه بیرون از Document Root وب‌سرور** قرار داده شوند. هیچ رمز یا کلید واقعی را در فایل‌های پروژه یا Git قرار ندهید.

## ۱) تنظیمات ضروری محیط تولید

نمونهٔ تنظیمات محیطی (نام مسیرها فقط نمونه است):

```bash
export NAWARA_APP_ENV=production
export NAWARA_DATA_DIR=/var/lib/nawara/data
export NAWARA_UPLOADS_DIR=/var/lib/nawara/uploads
export NAWARA_SESSION_SECURE=true
export NAWARA_SESSION_LIFETIME=86400
export NAWARA_MAX_UPLOAD_MB=50
export NAWARA_MAX_UPLOAD_TOTAL_MB=100
export NAWARA_MAX_UPLOAD_FILES=10
```

- `NAWARA_DATA_DIR` باید فقط برای کاربر سرویس PHP قابل خواندن/نوشتن باشد (`0750` برای پوشه و `0640` برای دیتابیس پیشنهاد می‌شود).
- `NAWARA_UPLOADS_DIR` باید بیرون از پوشهٔ public سایت باشد. فایل‌ها فقط از مسیر `file_manager.php` و پس از بررسی دسترسی دانلود می‌شوند.
- `NAWARA_APP_ENV=production` نمایش خطاهای PHP را خاموش می‌سازد. خطاها را از لاگ وب‌سرور/PHP بررسی کنید، نه از پاسخ کاربر.
- `NAWARA_SESSION_SECURE=true` فقط وقتی فعال شود که سایت واقعاً با HTTPS اجرا می‌شود؛ در تولید HTTPS اجباری است.
- در تنظیمات PHP وب‌سرور نیز `display_errors=Off`، `max_file_uploads` حداقل برابر با `NAWARA_MAX_UPLOAD_FILES` و `post_max_size` برابر یا بزرگ‌تر از سقف مجموع آپلود تنظیم شود. برخی خطاهای مربوط به اندازه/تعداد فایل پیش از اجرای کد برنامه رخ می‌دهند.

## ۲) ادمین نخستین

در یک دیتابیس کاملاً خالی، پیش از نخستین درخواست این متغیر را تنظیم کنید:

```bash
export NAWARA_INITIAL_ADMIN_PASSWORD='یک-رمز-بلند-و-تصادفی-حداقل-۱۲-حرفی'
```

اگر متغیر تنظیم نشود، برنامه یک رمز تصادفی موقت ایجاد و فقط در لاگ سرور می‌نویسد. پس از نخستین ورود، رمز را از طریق مدیریت کاربران تغییر دهید. رمز پیش‌فرض قدیمی نباید برای نصب تازه استفاده شود.

## ۳) حفاظت وب‌سرور

فایل‌های `.htaccess` در `data/` و `uploads/` برای Apache دسترسی مستقیم HTTP را مسدود می‌کنند. برای Nginx (یا هر وب‌سرور دیگر) همین سیاست را صریحاً اضافه کنید؛ `.htaccess` در Nginx اجرا نمی‌شود:

```nginx
location ~ ^/(data|uploads)/ {
    deny all;
    return 404;
}
```

حتی با این قاعده، بهترین روش همچنان انتقال دو پوشه با متغیرهای محیطی به بیرون از public root است.

## ۴) بکاپ و مهاجرت

مهاجرت‌های این مرحله افزایشی‌اند و در تراکنش اجرا می‌شوند؛ دادهٔ قدیمی را خودکار پاک نمی‌کنند. با آن هم، پیش از هر ارتقا بکاپ سالم و آزمایش‌شده بگیرید. برای SQLite، بکاپ باید هنگام خاموش بودن برنامه یا با روش backup سازگار با SQLite گرفته شود تا فایل WAL نیز نادیده گرفته نشود.

پس از انتقال، موارد زیر را بررسی کنید:

1. ورود ادمین و ایجاد یک کاربر آزمایشی.
2. دسترسی کاربر محدود تنها به پروژهٔ تعیین‌شده.
3. رد شدن درخواست بدون CSRF token.
4. ناتوانی کاربر Client در دیدن workspace داخلی تا زمانی که پورتال publish-gated مرحلهٔ بعد آماده شود.
5. دسترسی مستقیم HTTP به `data/` و `uploads/` باید `403` یا `404` بدهد.

## ۵) یادداشت دسترسی Client

در این مرحله حساب Client در دیتابیس و عضویت پروژه آماده است، اما همهٔ endpointهای قدیمی داخلی برای Client به شکل fail-closed بسته‌اند. این یک محدودیت عمدی امنیتی است: Client تا پیاده‌سازی پورتال جداگانه، فقط اطلاعاتی را که صریحاً publish/approve شده باشد خواهد دید؛ نه جزئیات داخلی پروژه، گزارش‌ها یا فایل‌ها.
